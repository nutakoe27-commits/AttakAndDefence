# Публикация в Яндекс Играх — архитектура, сервер, статистика

Документ отвечает на три вопроса: **как выложить игру в Яндекс Игры**, **что делать с сервером и какие мощности нужны для релиза**, **как собирать статистику для баланса**.

---

## 1. Ключевая идея: клиент на Яндексе, бэкенд у вас

Яндекс Игры хостят игру как **статический бандл** (архив с `index.html` в корне, ≤100 МБ), который открывается в iframe на домене Яндекса. Наша игра — **сервер-авторитарная** (вся симуляция PvP идёт на сервере), поэтому архитектура **разделяется на две части**:

```
┌─────────────────────────────┐         wss://          ┌──────────────────────────────┐
│  Клиент (статический бандл)  │  ───────────────────▶   │  Ваш бэкенд на VPS           │
│  хостится Яндексом в iframe  │   игровой WebSocket      │  • WS игровой сервер         │
│  games.yandex.ru/...         │                          │  • матчмейкинг + бот         │
│  + SDK Яндекс Игр            │                          │  • админка /admin            │
└─────────────────────────────┘                          │  • БД статистики (SQLite)    │
                                                          └──────────────────────────────┘
```

- **Клиент** (`public/index.html`, `css/`, `js/`) собирается билд-скриптом в `dist-yandex/` и загружается в Консоль разработчика Яндекса. Он подключается по WebSocket к вашему бэкенду.
- **Бэкенд** (`server/`) остаётся на вашем VPS: игровая симуляция, матчмейкинг, бот, админка и база статистики. В архив Яндекса он **не** попадает.

Это разрешено правилами: игры на Яндексе могут работать с внешним сервером (как все `.io`-игры). Запрещены только жёсткие ссылки на S3 Яндекса (п. 1.7) и ограничение игры по URL (п. 1.18) — у нас этого нет.

### ⚠️ Домен и HTTPS/WSS теперь обязательны

Раньше можно было играть по IP. Для Яндекса это **не сработает**: страница игры открывается по HTTPS, а браузер блокирует небезопасные WebSocket (`ws://`) со страницы `https://`. Значит бэкенд обязан быть доступен по **`wss://` (WebSocket поверх TLS)**, а для TLS-сертификата нужен **домен**.

Минимальный путь:
1. Купить домен (например `attackdefence.ru`), направить A-запись на IP вашего VPS.
2. Выпустить бесплатный TLS-сертификат Let's Encrypt (`certbot --nginx`, см. `DEPLOY.md` → «Будущий домен»).
3. nginx проксирует `wss://attackdefence.ru/ws` на игровой сервер (блок `location /ws` уже настроен в `DEPLOY.md`).

### Как собрать бандл под Яндекс

```bash
npm run build:yandex -- wss://attackdefence.ru/ws
# соберётся dist-yandex/ с index.html в корне, относительными путями,
# подключённым SDK и адресом вашего бэкенда
cd dist-yandex && zip -r ../attack-and-defence-yandex.zip . && cd ..
# attack-and-defence-yandex.zip загружаем в Консоль разработчика
```

Билд-скрипт проверяет: `index.html` в корне, относительные пути, SDK подключён, админка не попала в архив, размер < 100 МБ, имена файлов без пробелов и кириллицы (п. 1.21, 1.22).

### Что нужно сделать вам в Консоли разработчика (не код)

- **Монетизация РСЯ (п. 1.12):** обязательна для публикации. Interstitial и баннер уже вызываются в коде через SDK — вам нужно включить монетизацию в Консоли и пройти модерацию РСЯ.
- **Заполнить черновик (п. 5.2):** Название (уникальное, без слова «игра»/«game» — п. 6.5), «Об игре», «Как играть», Категории (Стратегия), Иконка и Обложка (**не скриншоты** — п. 5.6), скриншоты (реальный геймплей ≥70% — п. 5.1.1.2), поддерживаемые платформы (рекомендую **Десктоп + Мобильные**; ТВ — только если добавите управление пультом, п. 1.6.3).
- **Язык (п. 2.10, 2.14):** в игре русский. Выберите русский как язык черновика — этого достаточно для «локализации хотя бы на один язык». Автоопределение языка через SDK уже читается (`Ya.lang`); английскую локализацию можно добавить позже (строки вынести в словарь).
- **Возрастной рейтинг (п. 2.7):** фэнтезийные сражения без крови/жестокости → 6+ или 12+.
- **Иконка/обложка (п. 5.6, 8.3.3):** нарисовать отдельно (не скриншот, без рамок и скруглений).

### Мелочи, которые стоит доработать перед подачей

- **Звук.** Сейчас звука нет. Если добавите — обязательно глушить при `visibilitychange` и во время рекламы (крючок `gamePaused` уже есть), плюс кнопка отключения звука (п. 6.2).
- **Rewarded-реклама (опционально, п. 4.5).** Не добавлял намеренно: награда не должна влиять на PvP-баланс. Если захотите — давайте только косметику или бонус в одиночном режиме.
- **Консоль без ошибок (п. 6.4, рекомендованное).** На площадке Яндекса SDK грузится штатно. При открытии бандла вне Яндекса в консоли будет одна безобидная запись о неудачной загрузке SDK — на самой площадке её нет.

## 3. Сервер и мощности для релиза

### Сколько «весит» один матч

Симуляция идёт на сервере: **8 тиков/с**, до ~180 юнитов одновременно (2×90). Один матч — это лёгкая нагрузка на CPU: простая математика движения и боя, без физдвижка. Ориентир — **один матч ≈ 1–3% одного ядра** современного x86 vCPU.

### Рекомендации по железу

| Стадия | Одновременных матчей | Конфигурация VPS | Комментарий |
|---|---|---|---|
| **Старт / софт-запуск** | до ~30–50 | **2 vCPU, 2 ГБ RAM, 20 ГБ SSD** | С запасом. Node — один процесс, WS + симуляция + SQLite тянет спокойно |
| **Уверенный трафик** | ~100–150 | **4 vCPU, 4 ГБ RAM** | Апгрейд вертикально по мере роста |
| **Много трафика** | 300+ | горизонтальное масштабирование | см. ниже |

Память: каждый матч держит карту (46×30) и массивы юнитов — это десятки КБ. 1000 матчей ≈ считанные десятки МБ. Узкое место — **CPU**, не RAM. Сеть: снапшот ~2–6 КБ 8 раз/с на игрока → ~50–200 Кбит/с на игрока; сотня матчей ≈ 20–40 Мбит/с — обычный VPS-канал справляется.

**Вывод для релиза:** начните с **2 vCPU / 2 ГБ** (это ~200–500 ₽/мес у российских хостеров: Timeweb, Selectel, Yandex Cloud, VDSina). Этого хватит на первые сотни игроков. Мониторьте CPU (`htop`, метрики в админке) и апгрейдитесь вертикально.

### Когда понадобится масштабирование

Node — однопоточный, поэтому один процесс использует одно ядро. Чтобы задействовать N ядер:
1. Запустить **N инстансов** игрового сервера (по одному на ядро) за nginx.
2. **Sticky-сессии по WebSocket** (`ip_hash` или cookie), чтобы игрок и матч жили на одном инстансе.
3. Матчмейкинг тогда лучше вынести в общий слой (Redis для очереди), т.к. игроки на разных инстансах должны находить друг друга. На старте это **не нужно** — один инстанс закрывает первые сотни игроков.

### Обязательное для Яндекса

- **Домен + HTTPS/WSS** (см. раздел 1). Без этого клиент с площадки Яндекса не подключится к бэкенду.
- **Аптайм.** Если бэкенд лежит — игра на Яндексе не работает и рейтинг (п. 2.13) упадёт ниже 30 → снятие с публикации. Поставьте автоперезапуск (`systemd Restart=always`, уже в `DEPLOY.md`) и простой аптайм-мониторинг (UptimeRobot и т.п.).
- **CORS/Origin.** Игра открывается с домена Яндекса — сервер принимает WS без проверки Origin (по умолчанию так и есть). При желании можно вайтлистить `*.yandex.net/*.games.yandex.ru`.

## 4. Статистика и база данных для баланса

### Что собирается

По **каждому завершённому матчу** сервер пишет в БД:

- **Матч:** тип (pvp/бот/друг), длительность, число раундов, победитель, причина конца, сид карты, версия баланса.
- **По каждому игроку:** победа/поражение, убийства, потери, заработано/потрачено золота, HP базы, а также **разбивку по типам**:
  - сколько юнитов каждого типа выпущено и потеряно,
  - сколько построек каждого типа возведено,
  - на что потрачено золото (юниты / экономика / оборона).

### Почему SQLite

Для одного VPS и такой нагрузки **SQLite — оптимальный выбор**: не нужен отдельный сервер БД, нулевой оверхед, транзакции, надёжность. Реализовано на **встроенном `node:sqlite`** (Node ≥ 22.5) — **без единой npm-зависимости**. Файл БД: `server/data/stats.db` (в `.gitignore`, переживает обновления кода; включите его в бэкапы).

> Если на сервере Node старее 22.5 — модуль недоступен, и статистика молча отключается (игра работает как раньше). Обновите Node до 22 LTS, чтобы включить аналитику. Для очень больших нагрузок в будущем схема легко переносится на PostgreSQL.

### Аналитика в админке

Новая вкладка **«Аналитика»** (`/admin` → Аналитика) показывает всё для регулирования баланса, с фильтром по периоду (сутки/неделя/месяц/всё время):

- **Сводка:** число матчей, средняя длительность, среднее число раундов, ничьи.
- **Баланс сторон:** как часто побеждает левая vs правая база (здоровое значение ≈ 50/50; перекос сигналит о проблеме генерации/старта).
- **Юниты:** по каждому типу — сколько выпущено, **pick rate** (доля игроков, взявших юнита), **выживаемость**, **win rate** (винрейт взявших). Красный/зелёный цвет сразу показывает пере-/недосильные юниты.
- **Постройки:** построено всего, в среднем на игрока, pick rate, win rate.
- **Экономика:** средние траты на юнитов / экономику / оборону за матч.

Логика регулирования: если у юнита **высокий pick rate и высокий win rate** — он, вероятно, имбовый (поднимите цену / срежьте статы в редакторе баланса на вкладке «Баланс»). **Низкий pick + низкий win** — юнит слаб (усильте). Правки применяются к новым матчам без рестарта, а `balance_version` в статистике позволяет сравнивать эффект правок «до/после».

### API

- `GET /api/admin/stats?days=N` — агрегированная аналитика за N дней (0 = всё время). Требует токен админки.
- Данные пишутся автоматически в `Lobby.onMatchFinish` — ничего настраивать не нужно.

### Приватность

Мы храним **только игровую статистику и введённое имя**; никаких персональных данных Яндекс ID. Это соответствует требованиям и упрощает «Политику конфиденциальности» (п. 3.5), если решите её добавить.
